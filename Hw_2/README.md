# ДЗ 2.1. Ограничение CPU и памяти процесса: cgroups в Linux и аналог для macOS

Стенд: MacBook Pro, Apple M1 Pro (10 ядер: 8 производительных P + 2 энергоэффективных E), 16 ГБ, macOS 26.6.
macOS - сертифицированный UNIX (ядро XNU), поэтому все показано на нем, а Linux описан для сравнения.
Скриншоты сняты с окна Terminal на этой машине.

## Файлы

| Файл | Назначение |
|---|---|
| `scripts/maclimit.sh` | утилита: ограничивает CPU (в % ядра) и память (RSS) для новой команды или уже запущенного процесса, при превышении памяти - OOM kill |
| `scripts/memhog.sh` | занимает память по 10 МБ каждые 0.5 с, пока его не убьют |
| `scripts/cpuhog.sh` | N процессов с пустым циклом - чистый счет в режиме пользователя |

```bash
./scripts/maclimit.sh -c 50 -- ./scripts/cpuhog.sh 2 30   # 2 процесса делят 50% одного ядра
./scripts/maclimit.sh -m 200M -- ./scripts/memhog.sh      # OOM kill на 200 МБ
./scripts/maclimit.sh -c 20 -m 100M -p PID                # уже запущенный процесс
```

Скрипты на `/bin/bash` 3.2 и стандартных утилитах macOS (`ps`, `kill`, `awk`, `taskpolicy`), ничего ставить не нужно. `stress` (`brew install stress`) можно использовать как источник нагрузки, но не обязательно. Свои процессы ограничиваются без `sudo`.

## 1. cgroups и почему их нет в macOS

**cgroups** (control groups) - механизм ядра Linux: процессы объединяются в группу (каталог в `/sys/fs/cgroup`), и ядро ограничивает ресурсы всей группы: CPU, память, swap, ввод-вывод, число процессов. Потомки автоматически попадают в группу родителя и выйти из нее сами не могут. Пакет `cgroup-tools` - обертка над этими файлами:

```bash
# Linux, cgroup v2 - для сравнения, в macOS не запустить
sudo cgcreate -g cpu,memory:hw2                   # группа = каталог /sys/fs/cgroup/hw2
sudo cgset -r cpu.max="50000 100000" hw2          # 50 мс CPU на каждые 100 мс = 50% одного ядра
sudo cgset -r memory.max=200M hw2                 # больше 200 МБ в RAM выделить нельзя
sudo cgset -r memory.swap.max=0 hw2               # и в swap ничего: не хватило памяти - OOM kill
sudo cgexec -g cpu,memory:hw2 ./scripts/memhog.sh # запустить команду в группе
cat /sys/fs/cgroup/hw2/memory.events              # oom_kill 1
sudo dmesg | grep -i "killed process"             # Memory cgroup out of memory: Killed process ...
sudo cgdelete cpu,memory:hw2
```

В XNU cgroups нет: нет `/sys/fs/cgroup`, `cgroup-tools` не ставится ни через brew, ни иначе. По этой же причине Docker на маке запускает контейнеры внутри виртуальной машины с Linux. Что есть в macOS вместо этого:

| Механизм | Что делает | Почему не подходит |
|---|---|---|
| `nice`, `renice` | приоритет | только очередность, свободный CPU процесс все равно займет целиком |
| `taskpolicy -c background` | класс QoS: на Apple Silicon только E-ядра, низший приоритет (ДЗ 1, рис. 5) | ограничивает, *где* считать, а не *сколько*: на M1 Pro это до 200% (2 E-ядра) |
| `ulimit -t` | лимит CPU-секунд за все время, потом `SIGXCPU` | это общий счетчик, а не доля CPU |
| `ulimit -m` | лимит RSS | ядро его не соблюдает (так же, как и современный Linux) |
| jetsam (memorystatus) | убивает процессы, когда памяти не хватает всей системе | лимит на отдельный процесс система ставит своим службам через launchd, для команды из терминала штатного способа нет |

Штатно ограничить долю CPU и объем памяти произвольного процесса в macOS нельзя, поэтому `maclimit.sh` делает работу ядра Linux в пространстве пользователя. В Linux так же устроены `cpulimit` (CPU) и `earlyoom` / `systemd-oomd` (память).

## 2. Как устроен maclimit.sh

Раз в 100 мс (как период `cpu.max` по умолчанию) скрипт делает снимок `ps -A -o pid,ppid,rss,time,stat` и строит дерево: процесс и все его потомки по PPID. Это аналог группы. Для дерева он считает сумму RSS и сумму CPU-времени (user + sys), а дальше:

- **CPU - квота на период**, как `cpu.max`. На каждый период положено `CPU% x 100 мс` CPU-времени. Остаток квоты = остаток + квота - потрачено за прошлый период. Ушли в минус - `SIGSTOP` всему дереву, пока остаток не станет снова неотрицательным, потом `SIGCONT`. Копить квоту больше чем на один период нельзя. Лимит общий на дерево, а не на процесс: при `-c 50` один поток работает 100 мс и стоит 100 мс, а два потока за 100 мс работы тратят 200 мс квоты и стоят три периода - тоже 50% на двоих. В Linux при исчерпании квоты ядро снимает группу с CPU само (троттлинг), здесь вместо этого - сигналы.
- **Память - свой OOM killer.** Сумма RSS дерева больше лимита - `SIGKILL` самому большому процессу (OOM killer Linux тоже выбирает самый «тяжелый»). Скрипт пишет `maclimit: OOM: ...`, а команда завершается с кодом 137 = 128 + 9 (SIGKILL).
- **Ctrl+C:** для команды - завершить все дерево; для `-p PID` - снять ограничение (`SIGCONT`), процесс работает дальше. При любом выходе скрипт размораживает все дерево, чтобы не оставить процессы в состоянии T.
- Раз в секунду - строка потребления, после выхода - итог:

```
[  3 с] CPU   50.0%  RSS     7.2M / без лимита  стоп   8/10  OOM kill 0     (пример: -c 50, два процесса)
```

`CPU` - за последнюю секунду в процентах одного ядра, `RSS` - сумма по дереву и лимит, `стоп 8/10` - в скольких периодах из 10 дерево стояло (аналог `nr_throttled` из `cpu.stat`).

| | Linux: cgroups + cgroup-tools | macOS: maclimit.sh |
|---|---|---|
| группа | `cgcreate`, каталог в `/sys/fs/cgroup` | дерево процессов по PPID, пересчитывается каждые 100 мс |
| запуск в группе | `cgexec -g cpu,memory:hw2 cmd` | `maclimit.sh -c .. -m .. -- cmd` |
| уже запущенный процесс | `cgclassify -g cpu,memory:hw2 PID` | `maclimit.sh -c .. -m .. -p PID` |
| CPU | `cpu.max`: ядро троттлит группу | та же квота на период, через `SIGSTOP` / `SIGCONT` |
| память | `memory.max`: ядро не дает выделить больше и зовет OOM killer внутри группы | опрос RSS, превысили - `SIGKILL` самому большому |
| swap | `memory.swap.max` (в v1 `memory.memsw.limit_in_bytes`), `swapoff -a` | отключить нельзя, RSS не видит сжатое и вытесненное (п. 3.3) |
| точность | на каждом выделении памяти и каждом тике планировщика | раз в 100 мс: успеет выделить сверх лимита за 100 мс - будет убит чуть позже |
| можно ли сбежать | нет, потомки остаются в группе | процесс, сменивший родителя (демон), выпадает из дерева |
| права | root | свои процессы - без sudo |

## 3. Демонстрация

### 3.1 CPU

```bash
./scripts/maclimit.sh -c 50 -- ./scripts/cpuhog.sh 2 30
top -o cpu    # во втором окне
```

![Рис. 1. Два процесса под лимитом 50%](screenshots/01_cpu.png)

Без ограничения два `cpuhog` заняли бы 200% (два ядра целиком). С `-c 50` в строках `maclimit` CPU держится около 50%, а `стоп` около 7-8 из 10: на двоих они могут работать только четверть времени. В `top` у каждого процесса около 25%, и их состояние переключается между `running` и `stopped`. Итог в конце: `в среднем ~50% одного ядра при лимите 50%`.

То же для нескольких ядер: `-c 150 -- ./scripts/cpuhog.sh 4 30` дает 150% на четыре процесса. С `-b` процесс получает еще и QoS background: на M1 Pro он считает только на двух E-ядрах, так что больше 200% не получит при любом `-c`.

### 3.2 Память и OOM kill

```bash
./scripts/maclimit.sh -m 200M -- ./scripts/memhog.sh
echo $?    # 137
```

![Рис. 2. OOM kill на 200 МБ](screenshots/02_oom.png)

`memhog` каждые 0.5 с добавляет 10 МБ, RSS в строках `maclimit` растет. Как только сумма RSS перевалила за 200 МБ, скрипт убивает самый большой процесс дерева и пишет `maclimit: OOM: RSS ... > 200.0M, SIGKILL -> PID ...`, а в итоге - `команда убита сигналом 9 (SIGKILL), код 137` и `OOM kill: 1`.

Пик RSS чуть выше лимита: проверка раз в 100 мс, а не на каждом выделении, как в ядре Linux. С `stress` то же самое: `./scripts/maclimit.sh -m 200M -- stress --vm 1 --vm-bytes 500M --vm-keep` - убит рабочий процесс, а `stress` пишет `worker ... got signal 9` и выходит с кодом 1.

### 3.3 Swap: почему без настройки процесс бы не убили

В Linux `memory.max` ограничивает только RAM. Если swap включен, а `memory.swap.max` не задан, то при достижении лимита ядро вытесняет страницы группы в swap: процесс не убивают, он просто начинает тормозить. Чтобы показать OOM kill, swap группе запрещают (`memory.swap.max=0`, в v1 `memory.memsw.limit_in_bytes` равен `memory.limit_in_bytes`) или выключают совсем (`swapoff -a`). Насколько охотно ядро свопит, задает `vm.swappiness`.

В macOS swap выключить нельзя, и перед swap есть еще сжатие памяти:

```bash
sysctl vm.swapusage                       # swap динамический: файлы в /System/Volumes/VM, растут по мере нужды
vm_stat | grep -E "compressor|Swap"      # сколько страниц сжато, сколько ушло в swap и обратно
memory_pressure | tail -1                 # свободная память, %
```

![Рис. 3. Swap и сжатие памяти в macOS](screenshots/03_swap.png)

- Когда RAM не хватает, XNU сначала сжимает неактивные страницы (compressor), потом вытесняет сжатое в swap-файлы. Штатно это не отключить: swap ведет системная служба `dynamic_pager`, защищенная SIP.
- Ядро не убивает процесс за то, что тот занял «слишком много»: оно сжимает и свопит, а когда памяти не хватает всей системе, срабатывает jetsam или окно «Your system has run out of application memory». Поэтому OOM kill отдельного процесса в macOS делает только наш скрипт.
- RSS в `ps` - только то, что сейчас лежит в RAM. Сжатые и вытесненные страницы в него не входят. Под нехваткой памяти процесс может «спрятать» часть памяти в compressor и swap и превысить лимит `maclimit` - ровно как в Linux с `memory.max` без `memory.swap.max`. Полную память (RAM + сжатое + swap, `phys_footprint`) показывает Монитор активности в колонке «Память». Поэтому `memhog` пишет случайные байты: компрессор их почти не уменьшит.

### 3.4 Уже запущенный процесс

```bash
./scripts/memhog.sh 0 5 1 > /dev/null &      # растет на 5 МБ в секунду
./scripts/maclimit.sh -c 20 -m 100M -p $!
```

![Рис. 4. Ограничение работающего процесса по PID](screenshots/04_pid.png)

Скрипт берет процесс и всех его потомков и дальше ведет себя так же: на 100 МБ убивает. Если нажать Ctrl+C раньше, ограничение снимается, а процесс продолжает работать - тогда его надо завершить самому (`kill %1`). В Linux для этого есть `cgclassify`, и уже занятая до переноса память остается на счету старой группы.

## Выводы

- В Linux лимиты на группу процессов ставит ядро (cgroups), `cgroup-tools` - обертка: `cgcreate`, `cgset`, `cgexec`. Ядро же убивает процесс, когда памяти в группе не хватило (memcg OOM killer), а настройки swap решают, убьет ли оно процесс или начнет его свопить.
- В macOS (XNU) cgroups нет. Есть приоритеты и QoS (`nice`, `taskpolicy`) и системный jetsam, но нет лимита на долю CPU и объем памяти отдельного процесса.
- `maclimit.sh` повторяет cgroups в пространстве пользователя: квота CPU на период 100 мс через `SIGSTOP` / `SIGCONT` и свой OOM killer по RSS. На демонстрации CPU держится на заданном проценте, а `memhog` убит `SIGKILL` с кодом 137.
- Цена пользовательского ограничителя: опрос раз в 100 мс (память ненадолго превышает лимит), процесс может уйти из-под контроля, сменив родителя, а сжатая и вытесненная память в RSS не видна.

Источники: `man ps`, `man kill`, `man taskpolicy`, `man vm_stat`, `man memory_pressure`; документация ядра Linux `Documentation/admin-guide/cgroup-v2.rst` (`cpu.max`, `memory.max`, `memory.swap.max`, `memory.events`); `man cgcreate`, `man cgset`, `man cgexec`.
